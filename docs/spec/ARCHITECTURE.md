# System Architecture & Core Contracts

This document serves as the foundational architecture contract for HopaoEMS. All new features must adhere to these structural constraints.

## 1. UI Macro-Only Rendering Strategy
To ensure 100% UI consistency, direct usage of raw HTML tags (like `<div>`, `<table>`, `<button>`) in page templates is forbidden unless an existing macro cannot solve the problem.
- **Rule**: All forms, lists, cards, and buttons MUST use Jinja2 macros defined in `src/hopaoems/templates/macros/ui/`.
- **Key Macros**:
  - `ui_list_page()`
  - `ui_form_layout()`
  - `ui_table()`
  - `ui_button()`
  - `ui_input_field()`, `ui_select_field()`

## 2. JavaScript Integration Contract
- **Vanilla ES6+**: No heavy reactive frameworks (React, Vue).
- **Event Delegation**: Dynamic elements (like adding rows to a table) MUST use event delegation attached to the nearest static parent container.
- **Modularity**: Scripts are organized strictly by concern in `src/static/js/`.
- **DOM Dependencies**: Scripts expect predictable classes generated by UI macros (e.g., `.ui-table`, `.ui-btn`).

## 3. i18n (Internationalization) Contract
- **Hardcoded Strings**: ZERO hardcoded UI strings are allowed.
- **Translation Functions**: Always use `_('key')` or `t('key')` in Jinja2 templates.
- **Dictionary Source**: Keys map to `src/hopaoems/i18n/seed.zh-TW.json` and others.
- **Coverage**: Toolbars, table headers, button labels, toasts, placeholders, and error messages must all be translated.

## 4. RBAC (Role-Based Access Control)
- **Roles**: Distinct `operator` (read/write access) and `viewer` (read access).
- **Enforcement Layer**:
  1. **Route Level**: Modification endpoints (`POST`, `/edit`, `/new`, `/delete`) are guarded using the `@operator_required` backend decorator.
  2. **View Level**: Action UI components (Edit/Delete buttons, mutative forms) are wrapped in `{% if current_user.role == 'operator' %}` or handled natively by conditional macros.

## 5. Viewport Strategy: Single Scroll
- Interlocking full-height flexbox layouts ensure the main application container provides a **single global scrollbar**.
- **Constraint**: No internal scrolling boxes (`overflow-y: auto` inside main content panels) except for specialized UI domains (like a custom modal). This prevents "double scrollbar" UX traps. 
- Elements rely on CSS Grid and Flexbox with `min-height: 0` to defer scrolling up to the root scroll container.

## 6. CSS Architecture Strategy (The "3-File" Rule)
Styling is strictly centralized into three primary CSS pillars rather than scattered inline rules:
1. **Tokens/Variables (`tokens.css` or `vars.css`)**: Defines the color palette (e.g. `var(--color-primary)`), typography, sizing metrics, and spacing definitions. No styling logic; just variables.
2. **Layouts (`layout.css`)**: Defines structural grid/flex primitives used by macros (e.g., `.ui-stack`, `.ui-cluster`, `.ui-form-layout`, `.ui-main-panel`).
3. **Components (`components.css`)**: Defines the specific looks for discrete widgets (e.g., `.ui-btn`, `.ui-badge`, `.ui-table`).

*Any new CSS required must fit logically into these three domains. Inline `style="..."` is strictly prohibited except for dynamic structural calculations (like precise canvas coordinates or width percentages). Tailwind-style extensive utility usage in HTML is replaced by our UI Macros pointing to these 3 core definitions.*
